# 🧭 Discord AI Bot 開発における前提・基本原則 (Engineering Premises & Principles)

このドキュメントは、本プロジェクト（`discord-ai-bot`）においてAIエージェントおよび開発者がコードの追加・修正・リファクタリングを行う際に必ず遵守すべき**アーキテクチャの前提**と**設計・実装の基本原則**を定めたものです。

個別・具体的な禁止事項は [ban_list.md](file:///Users/Shadow/Documents/05%20%E9%96%8B%E7%99%BA/discord-ai-bot/.agents/rules/ban_list.md) に集約されています。本ドキュメントはその根底にある思想と原則を体系化しています。

## 1. システム・アーキテクチャの前提 (Foundational Architecture Prerequisites)

### 1.1 単一プロセス・独立Botアーキテクチャ
- **統合管理**: 本プロジェクトは、AIチャット（Ollama）、感情状態（EmotionState）、記憶システム（MemoryStore）、ゲーム（20の扉/うみがめ）、外部Web検索/天気を**単一の `commands.Bot` インスタンス（1つのPythonプロセス）**で統括しています。
- **プロセス競合の完全排除**: 同一の Discord Bot トークンを複数のプロセスで同時に Gateway 接続してはなりません（Interaction競合 `10062: Unknown interaction` やコマンド消去の原因となります）。
- **コマンド同期 (Command Sync)**:
  - グローバルコマンド（AI系: `/20doors`, `/umigame`, メッセージメニュー等）は `await bot.tree.sync()` で同期。
  - ギルド専用コマンドは、過去の古いギルドコマンドのクリーンアップを含めて `setup_hook()` で同期。
  - 同一トークンの複数プロセスで個別に `tree.sync()` を実行したり、`copy_global_to` で一方に押し込んではなりません。
- **マルチBot並行稼働時のGatewayイベント同報配信とログ・イベント分離**:
  - 同一ギルド内に複数のBot（例: `config_img` と `config_test-server`）が存在する場合、Discord Gateway の仕様により全メッセージ（他Botの発言や別チャンネルの会話）がすべてのBotプロセスに `MESSAGE_CREATE` イベントとして同報配信されます。
  - 各Botの `on_message` 最上流で `author.bot == True` や担当外チャンネル（`kind == "none"`）の通常雑談・他Bot宛て返信を `force_response` 計算前に `log.debug` で即座に破棄・早期スキップし、自Botが関与するチャンネル・メッセージのみを `log.info` の対象とすることで、ログの完全分離とクロストーク防止を徹底します（項目107）。
- **マルチBot並行稼働時の他Bot宛てメッセージ素通り遮断（五重防御）と状態分離**:
  - ユーザーが他Bot宛てに発言したメッセージ（他Botへのメンション、他Bot返信、他Bot名呼びかけ）を自Botが取り込むと、自Botの感情値（`scores`）、感情理由（`reason`）、吹き出しステータス（Activity）、Bio が関係ない会話で上書き・汚染されます。
  - 受信パイプライン（`on_message` 最上流、`_should_ignore`、`_process_queued_message`、`_run_emotion_update_for_message`、`_update_emotion_state`）の五重防御により、他Bot宛てメッセージを完全遮断して自Botの状態・ログを保護します（項目115）。
- **マルチBot並行稼働時の永続化ストレージ・DBの自動分離（Auto-Isolation）**:
  - 複数Botが同一ホスト上で並行稼働する際、ログだけでなく記憶DB（`memory_{config_name}.db`）、テーブル内ペルソナ名前空間（`cfg_persona_namespace`）、ゲームプール（`game_pool_{config_name}.json`）、感情/関係値（`emotion_state_{config_name}.json`, `user_relationships_{config_name}.json`）、投稿履歴（`img2chan_post_history_{config_name}.jsonl`）、プロセスロックファイル等の全永続化リソースを起動コンフィグ名（`config_name`）単位で自動的に分離します。個別コンフィグでパス指定がない場合でも衝突をゼロにし、主力Bot（`config_img`）の既存データは後方互換でそのまま保全します（項目112, 115）。
- **マルチBot並行稼働時のサーバー別メンバー自己紹介（Guild Member Bio）による同一トークン下での完全分離**:
  - 同一Botトークンを用いて複数コンフィグ（例: `config_img` と `config_test-server`）が並行稼働する際、全サーバー共通の `PATCH /applications/@me` で更新を行うと、最新のBotの感情で他サーバーの自己紹介が上書きされてしまいます。
  - 各Botは担当サーバー（`resolve_bot_guild_id()`）を特定し、Discord API のサーバー別メンバープロファイル（`PATCH /guilds/{guild_id}/members/@me`）に対して `json={"bio": bio_text}` を送信します。
  - これにより、Botトークンが同一であっても、各サーバー（本番サーバーでは【img】、テストサーバーでは【test】）ごとに独立した自己紹介が表示され、他サーバーの自己紹介を上書き汚染することを根本防止します。
  - ギルド未設定時やAPIエラー時は従来の `PATCH /applications/@me` へ安全にフォールバックする多重防御を配備。`.env` を使用せずコンフィグ直接設定（`EMOTION_BIO_ENABLED`, `EMOTION_BIO_LABEL`）を死守します（項目124）。

### 1.2 オブジェクトライフサイクルとデータスコープ
- **長期常駐スコープ (`OllamaChatCog` / `self`)**:
  - Bot全体のライフサイクルに紐づく状態（感情状態 `self.emotion_state`、関係値 `self.user_relationships`、キュー `self._reply_queue`、記憶ストア `self.memory_store` など）を保持・管理します。
  - 感情状態や関係値の参照・更新は必ず `self` 経由で行います。
- **短期メッセージスコープ (`MessageRuntime` / `runtime`)**:
  - 単一メッセージ処理（受信から返答生成・送信完了まで）の間だけ存在するコンテキスト・データクラスです。
  - ❌ `runtime` に `emotion_state` などの永続状態や未定義フィールドは存在しません。推測でフィールドを追加・参照してはなりません。

### 1.3 非同期イベントループとタイムラグ制約
- **3秒ルールの死守**: Discord API の Interaction トークン有効期限は **3秒** です。`setup_hook()` やイベントハンドラの同期ブロックで起動や応答が遅延すると、ユーザー操作が失効します。
- **重い処理のバックグラウンド化**: LLM推論、Webリサーチ、ファイルI/O、大量データ初期化などは、イベントループをブロックせず、非同期タスク（`asyncio.create_task`）やワーカーキューで処理します。

### 1.4 外部依存はすべて「非信頼境界」
- Ollama（ローカルLLM）、外部API（天気API、ジオコーディング、Chrome MCP、Webスクレイピング等）は、ネットワーク断、タイムアウト、レート制限、形式変更が日常的に起こりうる「非信頼境界」として扱います。
- 外部呼び出しは必ずフェイルセーフに構成し、Bot全体のクラッシュやメッセージループの停止を起こさないようにします。

### 1.5 モジュール分割とファイルサイズ制約 (50KB Rule)
- 肥大化したファイルは原則 **50KB 以下** を目安に責務別サブモジュールへと分割・パッケージ化します（例: `agent/`, `harness/agent/memory_manager/`, `emotion/`, `chat_prompt/`, `ollama/`, `reply_safety/`）。
- ハーネスアーキテクチャ（`harness/`）への移行が完了したドメイン（記憶マネージャー `harness/agent/memory_manager` 等）については、旧パスの後方互換スタブを完全に廃止・物理削除し、直接参照へと一本化します。各責務別モジュール（`storage/`, `extractor`, `retriever`, `summarizer`, `logic` 等）はすべて 50KB 未満（最大 24KB 以下）を厳格に死守します。

### 1.6 プロジェクト共通ユーティリティ基盤 (`lib/`) と後方互換性
- プロジェクト全体で横断的に利用される汎用基盤コードはリポジトリ直下の `lib/` ディレクトリに集約します。
- 主な共通モジュール：
  - `lib/json_utils.py`: 高速JSON読み込み（`orjson` 自動利用）、非同期読み込み（`load_json_async`）、アトミック書き込み（`save_json_atomic`, `save_json_atomic_async`）。
  - `lib/config_utils.py`: 型安全な設定値パーサー（`cfg`, `cfg_str`, `cfg_bool`, `cfg_int`, `cfg_float`, `cfg_int_set`, チャンネルID抽出等）。
  - `lib/text_utils.py`: 全角半角正規化（`normalize_text`）、比較用正規化（`normalize_compare_text`）、感嘆詞トリム（`strip_leading_interjections`）、実質第1節抽出（`extract_effective_first_clause`）、URL抽出・除去（`extract_urls`, `strip_urls`）、トークン・文字数切り詰め（`truncate_text`, `truncate_lines`）。
  - `lib/discord_utils.py`: メンション・入力テキスト正規化（`strip_discord_mentions`, `clean_user_input_text`）、絵文字正規化（`normalize_emoji_str`）、Discordオブジェクト安全アクセス（`author_id`, `channel_id`, `guild_id`, `content`, `display_name`, `snowflake_to_ts`, `message_created_at_ts`）。
- 各モジュールで `ZoneInfo("Asia/Tokyo")` を個別に生成したり、設定パース処理や一時ファイルアトミック書き込みを重複実装してはなりません。
- 既存の共通モジュール（`ollama_bot/common/config_helpers.py` 等）を `lib/` へ移行した場合は、旧モジュールを「後方互換アグリゲーター」として維持し、外部や既存コードからのインポートを絶対に破壊しないでください。

### 1.7 会話文脈（Context）パイプラインと返信ツリーの最優先保全（Anti-Hijack & Tree Isolation）
- **返信ツリー文脈の最優先性**: Discord 返信（Reply）において、ユーザーが特定の過去メッセージに対して返信している場合、その返信先ツリー親メッセージ（`latest_ref`）が一連の対話コンテキストの最優先軸となります。
- **目的語ハイジャック（話題乗っ取り）の完全排除**: チャンネル内で並行して進行している他ユーザーの雑談（例: 寿司の話題など）や直近メッセージから、目的語や固有名詞を勝手に吸い上げて返信ツリーに混ぜ込んではなりません。
- **親発言と対象メッセージの厳格な分離**: 返信時のプロンプト構築では、返信先となった親発言（`【返信元の相手発言】`）とユーザー自身の最新発言（`対象メッセージ: {clean_user_text}`）を明確に分割して提供し、AI自身の過去発言（「3Dの帆船が13時間...🤓」等）とユーザーの発言（「顔文字は使わない約束を守ろう」等）を合成してキメラ発言を出力する事故を防ぎます。
- **ユーザー訂正に対する即時自己修正**: ユーザーがAIの解釈・前提を訂正・否定（「〜ではない」「〜って言ってるのだけど」等）した場合、AIは直前の自らの発言や解釈スタンス（「重い」「しんどい」等）に固執してはならず、素直に誤解を認めて相手の提示した事実・感情のみに沿った返答に即時切り替えます。

### 1.8 会話中の不明点調査（3段階フォールバック）と自然対話パイプライン
- **3段階フォールバック規約**: ユーザーとの会話中に不明な点や評判の確認が必要になった場合（例: 作品の特定のパートが面白いかどうか等）、以下の順序で多層防御フォールバックを行います：
  1. **第1段階（記憶DB検索）**: `MemoryStore`（長期記憶・SQLite/ベクトル/FTS5）から関連情報を検索し、過去の会話や体験がないか確認する。
  2. **第2段階（Web自然調査: Topic Investigation）**: 記憶に該当がない場合のみインターネット検索を実行し、世間の評判や実態を確認する。
     - ⚠️ **ファクトチェック形式の絶対禁止**: 外部調査（`topic_investigation.py`）を用いても、Xのコミュニティノートや検証レポートのような硬い見出し・形式・報告調の前置き（「〜と確認されました」等）は一切使わず、1〜2文の自然な会話・雑談としてネット評判を取り入れます。
  3. **第3段階（不知・不確実性の素直な表明）**: 調査しても情報が不十分、あるいは自身に体験がない場合は、知ったかぶりや勝手な属性捏造をせず、「ネットの評判だと〜らしいね」「自分はやったことないけど〜みたい」「確認できた範囲では〜」と素直に不確実性を表明します。
- **行動指針・約束・ルール文脈の除外**: 「約束」「守って」「使わない」「しよう」「禁止」などの行動指針・ルール指摘の文脈に「楽しく」「面白く」などの形容詞が含まれていても、トピック評価問い合わせと誤判定してWeb検索を誤爆させてはなりません。

### 1.9 オウム返しガードの受容保護とリトライプロンプトの完全性保証
- **オウム返しガードの受容・ツッコミ保護（Validate First）**:
  - 短い単語・名詞・ボケ（20文字以下。例:「ガッツギア ハンバーグ軍艦味」）に対して、AIが「〜か…！」「〜とは…！」「〜って…！」「〜ですか…！」「〜ですね…！」などの感嘆・ツッコミ語尾（`_is_short_noun_reaction_clause`）で受容し、その後ろに十分な展開（20文字以上）を持つ返答は、オウム返し（`looks_like_parrot_reply`）と誤認してはなりません。
  - ただし、語尾だけ変えたような全体丸写し復唱（類似度 0.85 以上）は、承諾句や受容句があっても確実にオウム返しとして遮断する二重防御を維持します。
- **リトライプロンプトにおける対象メッセージの死守**:
  - リトライプロンプトスリム化（`_slim_base_prompt_for_retry`）において、ユーザー間返信プロンプト（`【会話の状況（ユーザー同士のやり取り）】`）ブロック全体を正規表現で丸ごと消去してはなりません（内部のメタ注意文のみを除去すること）。
  - 万が一プロンプトから `対象メッセージ` が欠落した場合は、元のベースプロンプトから自動抽出・復元する多重防御を施します。
- **リトライプロンプトへの思考抑止指示の徹底適用**:
  - 各リトライプロンプト関数（`build_parrot_retry_prompt` 等）すべてにおいて、末尾に `append_chat_reply_output_suffix(...)` を適用し、推論モデル（Qwen 3.6等）が思考迷走（`<think>` タグ暴走）に陥って Modelfile 内の例文（「おはよう」「甘いものが好き」等）を最新発言と誤認してパッチワーク優等生返答を出力する事態を根本遮断します。

### 1.10 コンフィグ駆動原則と人格非依存の共通層（Config-Driven & Persona-Agnostic Core）
- **設定駆動による人格切り替え**: Botのキャラクター性、一人称、口調、語尾、フォールバック台詞、正規表現パターン、除外キーワード等の人格依存要素は、すべて各コンフィグファイル（`config_img.py`, `config_shanks.py` 等）のパラメータ定義によって切り替えるのが基本設計です。
- **共通モジュールからのハードコード完全排除**: `ollama_bot/`（`common/`, `lifecycle/`, `emotion/`, `reply_safety/` 等）や `lib/` などの共通処理層に、特定の人格名（コイトフクマル、小糸、シャンクス等）や特定の口癖・語尾・台詞（「ぴゃっ」「なんですよ」「だろ」「なァ」等）を直接ハードコードして分岐させてはなりません。
- **動的パラメータ解決と中立フォールバック**:
  - キャラクター固有の振る舞いは必ず `cfg(...)` 経由で動的に取得・解決します。
  - 設定値が存在しない場合の共通層のフォールバックは、どのキャラクターでも破綻しない中立な日本語（例: 「うまく返せなかったな…もう一回言ってくれ。」「そのあたりについては詳しくないので、正直よく分からないんだ。」等）を提供し、特定ペルソナへの依存を徹底して排除してください。

### 1.11 設定提示・解説文の受容とリトライ時直前発言コピペ遮断（Explanation Reception & Anti-Echo Loop）
- **設定・情報提供に対する受容**: ユーザーが用語やキャラクター・作品の設定・解説（『〜とは、〜の登場人物』等）を提示してくれた場合、文中の単語に『その名前は知らない』と辞書的確認やシラ切りで会話を拒絶することを禁止し、提示された設定やエピソードに素直に興味・感想・リアクションを述べます。
- **リトライプロンプトからの直前発言完全除去**: 類似・オウム返しリトライ時、プロンプトスリム化（`_slim_base_prompt_for_retry`）で `直前のAI発言:` や質問注記を完全に除去し、小型推論モデルが手元の直前発言をそのまま丸コピペ出力する事態を根本遮断します。
- **リトライ結果再検証パイプライン（多重防御）**: リトライ結果（`retried`）に対しても直前発言との同一・酷似やオウム返しを再検証し、問題があればキャラクター口調の安全フォールバックへ倒す多重防御を維持します。

### 1.12 サーバーメンバー言及・人物評におけるメタ困惑排除と具体的キャラクター人物像の言語化（Third-Party Representation & De-Excusing）
- **恒久的所感（thought）からのメタ困惑排除**: サーバーメンバーについての印象や感想を質問された際、過去の断片的な一時的困惑メモ（「急に名前を聞かれて〜」等）を恒久的人物所感（`thought`）へ保存したりプロンプトへ注入してはなりません（`is_meta_confusion_thought` で完全排除）。
- **第三者人物像の自動言語化**: 関係性パラメータ（親愛度、信頼度、憎しみ等）から、その相手が自分にとってどのような存在か（例: 「いつもからかわれて警戒している相手」「心を開いて安心できる常連さん」等）の具体的キャラクター人物像（`describe_relationship_for_third_party`）を自動言語化してプロンプトへ注入し、対話相手と話題の第三者を厳密に分離します。
- **返信プレフィックス完全除去と意見質問ツッコミ除外**: 返信プレフィックスは `re.DOTALL` で完全に除去し、意見質問（「どう思う？」等）で自発言ツッコミ（`is_self_tsukkomi`）が誤爆して過去発言の言い訳だけで返答を終える事態を防ぎます。

### 1.13 挨拶・自己紹介プロトコル保護と感情コンテキスト引きずられ防止（Greeting Safe-Zone & Emotion Isolation）
- **挨拶・自己紹介プロトコルのオウム返し除外**: 初対面の挨拶や自己紹介（「初めまして、〇〇と言います。仲良くしましょう」）に対して、AIが「初めまして、〇〇さん！仲良くしましょうね…！」と挨拶や名前を呼び返して応答する自然な対話プロトコルを、冒頭トピックエコーや共通文字比率（`reused_ratio >= 0.55`）でオウム返しと過剰検知してフォールバック台詞へ転落させてはなりません。
- **友好的挨拶に対するBADリアクション安全抑止**: 直前会話のセクハラ・攻撃的発言等によってBotの内部感情が極度の警戒・恐怖（`fear` 等）状態になっていたとしても、別ユーザーや新しい友好的挨拶（「初めまして」「こんにちは」等）に対して警戒心を引きずって `BAD` リアクション（`:Badmood:` 等）を誤爆付与してはなりません（コード側の安全抑止ガード `_is_friendly_or_greeting_message` ＋感情分類器プロンプトガイダンス）。

### 1.14 質問・意見照会におけるサーバーメンバー最優先照合（User-First Resolution）
- **サーバーメンバー最優先照合**: ユーザーから「〇〇についてどう思う？」「〇〇って知ってる？」等と意見や印象、人物についての質問を受けた際、一般名詞やWeb検索に先立ってDiscordサーバーメンバー一覧・プロファイルDBとの照合を最優先（User-First）で行います。
- **Web検索バイパスと仲間関係性の注入**: サーバーメンバーに該当する場合は、一般トピック向けのWeb検索パイプラインを即座にバイパス（スキップ）し、仲間としての関係性パラメータや人物像（`describe_relationship_for_third_party`）を最優先でプロンプトに注入します。該当メンバーが存在しないことが確認された場合に初めて、Web自然調査や一般名詞解釈へ安全にフォールバックさせます。

### 1.15 自立話題・質問における話題引きずり防止とトピック隔離（Topic Isolation）
- **短文自立話題の判定保護**: 指示語（「それ」「これ」等）を持たない新規の疑問・質問・挨拶等は、短文（14文字以下）であっても文脈判定をスキップして無条件FOLLOWと判定せず、自立話題（`is_standalone_topic`）として厳格に扱います。
- **記憶検索クエリの自立化**: 記憶DB（MemoryStore）検索において、自立話題の場合は直前AI発言を強制合成（`f"{last_assistant_text} {user_text}"`）せずユーザー発言単体で検索し、過去の無関係な記憶の混入を防止します。
- **直前コンテキストの物理的除外（トピック隔離）**: 自立話題時のプロンプト構築では、直前AI発言、直近の会話履歴、チャンネル会話要約を物理的に完全除外し（トピック隔離）、小型推論モデルが手元の直前発言単語を拾って前の話題を引きずる現象を根本遮断します。

### 1.16 ユーザー教示文におけるWeb検索遮断と話題転換（BREAK）時長期記憶想起保全・無関係記憶全選択ガード
- **教示文でのWeb検索誤爆防止**: ユーザーが用語やキャラクター・作品の設定、人物像（「〜とは、…です」「〜の名称です」「覚えてください」等）を教えている教示・定義文（`looks_like_user_teaching_or_definition`）では、文中の「とは」や年号・日付（2026年等）に反応して質問と誤認し、Web検索（`needs_research`）を誤爆起動させてはなりません。ユーザーから知識をインプットされている場面では検索を遮断し、対話と記憶保存フローを優先します。
- **話題転換（BREAK）時の長期記憶想起保全**: 直前の会話と別話題であると判定された話題転換（`flow == "BREAK"`）かつWeb調査の判定となった場合でも、専用プロンプト関数で記憶検索を蒸発させず、`_generate_break_reply(..., skip_model=needs_research)` を統一経由させて `get_relevant_memories` による MemoryStore からの長期記憶想起を確実に実行し、プロンプトへ組み込みます。
- **教示文における無関係記憶全選択ガード**: 小型推論モデル（Qwen 3B等）が教示文に対して候補メモリを無差別に全選択（`[0, 1, 2]`）して混入させるバグに対し、教示内容のキーワードと直接一致しない過去記憶を事後フィルター（`_post_filter_selected_memories`）で確実に除外します。これにより、新しいキャラクターや設定を教えている最中に無関係な過去記憶（ワス先輩等）が混入してAIが混同する事故を根本遮断します。

### 1.17 エージェント・ハーネス設計（Harness Architecture）とプロンプト・パーサーの完全集約
- **ハーネス階層アーキテクチャの定義**: 本Botは自律推論・行動および評価・安全性を高めるため、明確なハーネス構造（実行基盤／テストハーネス）に基づいて設計・配置します。
  1. **実行基盤（エージェント本体）**:
     - **1-1. コンテキスト構築（知覚・記憶の引き出し / フェーズ1）** (`harness/agent/prompt_parser/prompt_manager/`):
       - システムプロンプト動的生成、短期会話履歴（`history_helpers.py`）、返信ツリー文脈（`context_helpers.py`）、長期記憶・RAG想起（`chat_prompt_logic.py`, `working_memory.py`）、ユーザープロファイル・関心事（`user_profile_logic.py`, `user_interest_logic.py`, `prospective_memory.py`）。
     - **1-2. 推論と計画立案（Thought / フェーズ2）** (`harness/agent/prompt_parser/parser/`):
       - 返信ヘルパー・推論補助（`reply_helpers.py`）、口癖・ペルソナポリシー（`habit_policy.py`）、出力パーサー・安全性ガード（`reply_guards.py`）。
     - **1-3. ツール選択と実行（Action / フェーズ3）** (`harness/agent/tool_registry/`):
       - ツールカタログ・実行エンジン（`ToolRegistry`, `ToolExecutor`）、Web調査（`web_research/`）、気象情報（`weather_helpers.py`, 国内気象MCP）、ファクトチェックMCP（`FactCheckMCPServer`, `FactCheckMCPClient`, `FactCheckToolAdapter`）、ゲーム実行（`game_pool_manager.py`, `umigame_helpers.py`, `singing_helpers.py`）、外部連携アダプター群。
     - **1-4. 結果の観察と評価（Observation / フェーズ4）** (`harness/agent/prompt_parser/observation/`):
       - ツール実行・環境結果の観察基盤（`ObservationProcessor`, `ObservationEvaluator`, `LoopDetector`, `ObservationSynthesizer`）に加え、Bot固有の検証・評価機能群（`WebObservationEvaluator`, `FactCheckEvaluator`, `FeedbackObserver`, `ReplyObservationEvaluator`, `ReflectionEvaluator`）。
     - **1-5. オーケストレーター（フロー統括）** (`harness/agent/orchestrator/`):
       - フェーズ1〜5の自律制御ループ、ステートマシン、再試行差し戻し制御。
     - **1-6. 記憶マネージャー（Memory Manager / 永続記憶・DB）** (`harness/agent/memory_manager/`):
       - SQLite・ベクトル検索（`sqlite_vec` / FTS5）ストレージ層（`storage/`）、記憶抽出（`extractor.py`）、関連記憶想起（`retriever.py`）、会話要約・プロファイル更新（`summarizer.py`）、定期内省（`reflection.py`）、および統合ファサード（`logic.py`）。旧後方互換レイヤーは完全廃止・物理削除し、直接参照へと一本化。
  2. **テストハーネス（評価・安全性基盤）**:
     - **2-1. サンドボックス実行環境**（隔離実行・権限制限）
     - **2-2. テレメトリ・オブザーバビリティ**（分散トレース、トークン計測、ログ永続化）
     - **2-3. エバリュエーター**（アサーション、LLM-as-a-Judge、状態検証）
- **プロンプトマネージャー＆パーサーの一元管理**:
  - システムプロンプト動的生成（`system_prompts.py`）、中間分析・日時文脈プロンプト（`analysis_prompts.py`）、リトライ時スリム化プロンプト（`retry_prompts.py`）、文脈合成（`builder.py`）、トークン予算管理（`budget.py`）、出力パース・サニタイズ（`parser/`）の全ロジックは `harness/agent/prompt_parser/` 配下の4階層に完全集約します。
  - `ollama_bot/` 内に独自のシステムプロンプト文字列やパースロジックを散乱させてはなりません。
- **50KBルールと新ハーネスパス直接参照への一本化（フォワーダー完全撤廃）**:
  - 各モジュールは単一責任の原則に従って適切に分割し、原則 **50KB 未満** を厳格に遵守します。
  - 旧パス（`ollama_bot/common/` や `ollama_bot/ollama_chat_/`）に存在していた後方互換フォワーダーは完全撤廃（物理削除）されました。プロダクションコード・テストコード・設定ファイル等を問わず、すべての参照・インポートおよびモックは新ハーネスパス（`harness/agent/...` や `lib/...`）を直接指定し、撤廃済みの旧パスへの逆参照や再新設を固く禁止します。
- **統一ログ接頭辞 `[prompt-manager]` / `[tool-registry]` / `[observation]` の徹底**:
  - プロンプトマネージャー（`[prompt-manager]`）、ツールレジストリ（`[tool-registry]`）、結果観察・評価（`[observation]`）などの各フェーズにおいて、トレーサビリティおよびテレメトリ監視性向上のため、統一ログ接頭辞を必ず付与します。

### 1.18 プロンプト処理・RAG統合パイプライン仕様（Prompt Processing & RAG Integration Pipeline Specification）
- **エンドツーエンド処理パイプラインの定義**: ユーザーからのプロンプト受付からAI応答出力に至る処理は、以下の8段階の決定論的・多層防御パイプラインとして実行されます：
  1. **入力正規化とスレッド特定**: メンション・入力ノイズの正規化（`lib.discord_utils`）、会話スレッドの特定・並行スレッドの分離（`ThreadTracker.match_thread`）、リプライチェーン（`collect_reply_chain`）による返信先親メッセージの同定。
  2. **短期記憶（Short-term Memory）の抽出と文脈保護**: チャンネル直近の会話履歴（`context_lines`）をキャッシュから取得。返信ツリーが存在する場合は親メッセージ（`latest_ref`）を最優先文脈として保護し、並行する無関係な他ユーザー雑談からの目的語ハイジャックを遮断。
  3. **長期記憶/RAG（Long-term Memory & Episodic Retrieval）の検索**: 自立話題（`is_standalone_topic`）判定を行い、話題引きずりを防ぐ検索クエリを生成。埋め込みモデル（BGE-M3, 1024次元）によるベクトル類似度検索＋FTS5全文検索で `MemoryStore` から候補記憶（`memories`）、出来事記憶（`memory_episodes`）、未来の意図（`future_prompts`）を想起。
  4. **事前知識・言及人物の事前解決（User-First Resolution & Entity Linking）**: 会話中に登場するサーバーメンバー名を最優先照合（`resolve_and_format_mentioned_users`）。関係性パラメータ（親愛度、信頼度、憎しみ等）から具体的キャラクター人物像（`describe_relationship_for_third_party`）を言語化し、対話相手と話題の主を厳密分離。
  5. **事前分析エージェント（Middle-LLM Context Analyzer）による選別・内省**: 軽量構造化モデル（`middle-llm`）を起動し、①意図判定（`intent`）、②AI言及判定（`target_is_ai`）、③**メモリ選別（`selected_indices`）**（候補の中から今回の返答に真に関連する記憶のみを抽出）、④内省補助（`emotion_focus`, `reply_strategy`, `avoid`）、⑤自己整合性監査（`persona_risk`, `consistency_correction`）、⑥会話破綻修復（`is_breakdown`）、⑦不確実性（`uncertainty_level`）を1回のJSON呼び出しで判定。
  6. **システムプロンプトの動的生成（Dynamic System Prompt Generation）**: 現在日時（サーバ時刻JST）、キャラクター設定（一人称、口調、世界観）、口調ガード、返答形式、時間帯補足を `system_prompts.py` で動的に組み立て。
  7. **コンテキスト予算管理とプロンプト結合（Budgeting & Prompt Assembly）**: トークン予算（`_trim_prompt_inputs`）に基づき、短期記憶・長期記憶・要約・エピソードを安全にトリム。現在の感情状態（`EmotionState`）、相手との関係性（`UserRelationship`）、核となる価値観（Core beliefs）、選別済み長期記憶、短期履歴、返信ツリー、言及メンバー情報、対話相手情報、対象メッセージ、内省メモを `builder.py` で結合。
  8. **推論実行と出力パーサーによる多重防御（Inference & OutputParser）**: メインモデルで応答生成。思考タグの未完切断時は `salvage` でセリフを救出。`OutputParser.sanitize` で思考タグ、制御行、指示漏れ、箇条書き、Markdown、相手誤認呼びかけ、Bot自己メンション、話者名付きエコー行を徹底除去。`OutputParser.validate_safety` でオウム返し、文末途切れ、外国語、前発言酷似、キャラ崩壊、時間帯矛盾等を検証し、安全な対話応答のみをDiscordへ送信。

### 1.19 ハーネス設計と自律エージェント5段階処理フロー（Agent Harness & Orchestration Architecture）
- **5段階エージェント内部処理フロー**: ユーザーからの指示・メッセージを受け取ってから最終応答を出力するまでの処理は、ハーネスアーキテクチャに基づき以下の5段階ループとして統括されます：
  1. **コンテキスト構築（Context / 知覚・記憶の引き出し）**: システムプロンプト動的生成、短期会話履歴・返信ツリー保護、長期記憶（RAG/ベクトルDB/FTS5）検索、事前知識（サーバーメンバーUser-First解決・関係値言語化 `relationship_prompts.py`）、事前分析（Middle-LLMによる意図・メモリ選別・内省）を結合（`harness/agent/prompt_parser/prompt_manager/`）。動的 `cfg` 解決を担保。
  2. **推論と計画立案（Thought）**: 組み立てられたコンテキストを元に、LLM（コアエンジン）が目的達成のための思考とアクション計画を策定（`harness/agent/prompt_parser/parser/`）。サニタイザー（`sanitizer.py`）、思考タグ除去、プレースホルダー検知（`looks_like_placeholder_thought`）、過去ログ丸写し検知（`looks_like_copied_log_appraisal`）を集約。
  3. **ツール選択と実行（Action）**: Function Calling等に基づきツール実行エンジン（正本パス: `harness/agent/tool_registry/`）が外部API、MCP、Web調査（`web_research/`）、国内気象MCP、ゲーム実行（`game_pool_manager.py`, `umigame_helpers.py`, `singing_helpers.py`）を安全に呼び出して干渉。旧パス（`prompt_parser/tool_registry/` 等）には `sys.modules` エイリアス同期 shim を配備してモック・テスト破壊を防止。
  4. **結果の観察と評価（Observation）**: ツール実行結果やLLM出力を `harness/agent/observation/`（`ObservationProcessor`, `ObservationEvaluator`, `LoopDetector`）が観察・評価。
     - **感情観察**（`EmotionObservationEvaluator`）: 中国語・簡体字混入排除、架空事実捏造防止、プロンプト感情理由隔離（項目87, 90）。
     - **Web調査観察**（`WebObservationEvaluator`）: 目的語ハイジャック検知（項目75）、ノイズ除外、情報十分性判定。
     - **ファクトチェック観察**（`FactCheckEvaluator`）: 真偽性・信頼度判定。
     - **ユーザー環境フィードバック観察**（`FeedbackObserver`）: Discordリアクションによる感情・関係値評価。
     - **応答・思考観察**（`ReplyObservationEvaluator`）: オウム返し、思考漏洩、文末途切れ、不知スキップ判定（項目77）とリトライ差し戻しプロンプト生成。
     - **内省観察**（`ReflectionEvaluator`）: 第三者名呼称誤認防止バリデーション（項目93）。
     - 判定が不十分またはエラーループ時は、フェーズ2（Thought）に戻って修正・再試行。
  5. **最終応答の生成（Final Response）**: 観察・推論ループを経て十分な情報が揃った段階で最終返答を生成・サニタイズ（OutputParser）してDiscordへ送信し、対話要約をメモリへ永続化。
- **オーケストレーター100%化と旧直接呼び出しフォールバックの完全撤廃**:
  - 返信生成パイプラインはすべて `AgentOrchestrator`（`harness/agent/orchestrator/`）を経由させ、旧来の直接モデル二重呼び出しコードを完全撤廃します。一過性エラーはオーケストレーター直下で包括的にハンドリングし、タイムアウトフォールバックへ安全に遷移させます（項目110, 117）。
- **テストハーネス（評価・安全性基盤）の配備**:
  - `harness/agent/test_harness/` 配下にサンドボックス実行環境（`sandbox/`）、テレメトリ・オブザーバビリティ（`telemetry/`）、エバリュエーター（`evaluator/`: MechanicalAssertion, LLMAsAJudge, EnvironmentVerifier）を配備し、エージェントの挙動を監視・検証・保護します。

## 2. 開発・設計のコア原則 (Core Engineering Principles)

### 📌 原則1: 既存構造の尊重と事前調査（Look Before You Leap）
- **確認前のコーディング禁止**: クラス、メソッド、データクラス（`ollama_chat_types.py` 等）を触る前に、必ず `view_file` や `grep_search` で型定義と既存実装を確認してください。
- **安全な属性アクセス**: 動的オブジェクトや外部から渡されたデータは `getattr(obj, "prop", default)` や辞書 `.get()` で安全に取得してください。
- **重複ロジックの排除**: 既存の仕組み（非同期感情更新キュー、記憶検索パイプラインなど）が存在する場合、車輪の再発明や並行する即時処理を勝手に追加しないでください。

### 📌 原則2: 副次効果とパイプラインの完全保全（Preserve Side-Effects & Event Pipelines）
- **副作用の置き去り禁止**: 非同期処理を同期化したり、ショートカット処理を導入する際は、元のタスクが担っていた「副次効果（Presence/アクティビティ更新、ニックネーム同期、リアクション付与、キュー整合性など）」を漏れなく移行・維持してください。
- **全呼び出し経路の検証**: 状態更新（感情・関係値など）のフローを変更した場合は、すべての呼び出し経路からDiscord上の見た目（Presence/Nickname）に確実に反映されることを確認してください。

### 📌 原則3: 多重防御と安全なフォールバック（Defensive Programming & Graceful Degradation）
- **包括的例外ハンドリング**: 外部通信やI/Oを行う関数は、`try...except (aiohttp.ClientError, asyncio.TimeoutError, Exception) as e:` で捕捉し、適切なエラーログ（`log.warning`/`log.exception`）を記録した上で安全な戻り値（`None` や空構造）を返してください。
- **多層フォールバック**: 呼び出し元（ハンドラ側）でも、データ取得失敗時に安全なデフォルト応答（`OLLAMA_UNKNOWN_FACT_FALLBACK` や定型文）へ倒れる二重防御を実装してください。

### 📌 原則4: 堅牢な状態永続化とオフライン時間減衰（Atomic Persistence & Time Decay）
- **アトミック同期保存**: 感情状態や関係値のファイル保存は、プロセス強制終了（`SIGTERM`/`SIGKILL`）でもデータが破損・消失しないよう、`lib.json_utils` の即時アトミック保存（`save_json_atomic` / `save_json_atomic_async`）を使用してください。
- **オフライン経過時間の減衰計算**: 起動時のデータ復元では、前回の保存時刻からの経過時間（`now - last_save_ts`）を計算し、経過時間に応じた感情減衰を適用して平常（`neutral`）へ自然に回帰させてください。

### 📌 原則5: 入力の厳格な正規化と前処理（Strict Input Normalization）
- **ノイズの完全除去**: ユーザー発話から地名・キーワード・日時などのパラメータを抽出する際は、正規表現マッチングの前にDiscordメンション（`<@id>`）、接続詞（「じゃあ」「では」等）、助詞（「の」「は」「で」）、日付表現（「今日」「明日」）を厳密に正規化・トリミングしてください。
- **静的キャッシュの優先活用**: 日本の47都道府県や主要都市の座標のように静的に確定しているデータはプリセットキャッシュ（`_PRESET_COORDINATES` 等）で即時解決し、外部APIへの不要な依存と遅延を極力削減してください。

### 📌 原則6: Discord API 制約の絶対遵守（Discord API Constraints Compliance）
- **Context Menu 上限（最大5個/ギルド）**: 1ギルドあたりの Message Context Menu は最大5個です。AI機能と管理機能の合計が5個を超えないよう厳密に配分・管理してください。
- **単一設定値への依存排除**: `GUILD_ID` などの単一設定値だけに依存せず、`self.bot.guilds` へのフォールバックを行って権限のある全サーバーで安全に動作するようにしてください。

### 📌 原則7: 静的型付けと mypy 厳格運用の徹底（Static Typing & Type Safety First）
- **完全な型アノテーション（PEP 484/585/604）**: すべての関数、メソッド、データクラス、クラス属性に引数型と戻り値型を明記してください。`Any` や `object` の安易な利用を避け、Union（`X | None`）や具体的なコレクション型（`list[str]`, `dict[str, Any]`）を使用してください。

- **Protocol による Mixin 型安全の確保**: Cog Mixin 間の相互呼び出しは `ollama_chat_types.py` の `OllamaChatProtocol` に定義し、`TYPE_CHECKING` 下で継承して型安全と多重継承メタクラス制約（Discord.py `CogMeta`）の両立を維持してください。
